# code-review

## 审查顺序（先重后轻）
1. **正确性**：逻辑是否实现需求；边界与异常路径（空值、并发、超时、重试）是否处理；与 plan-spec 验收标准逐条对。
2. **安全**：输入校验与注入面、鉴权/越权、密钥与敏感信息是否进代码或日志、依赖新增是否可信。发现疑似密钥立即标为最高严重度。
3. **数据与兼容**：迁移是否可回滚、接口变更是否破坏既有调用方、默认值变化的连锁影响。
4. **项目约定**：命名、分层、错误处理、日志风格与仓库既有模式一致（以 repo-context 的结论为准，不拿通用习惯压项目习惯）。
5. **可维护性**：重复、过长函数、无意义抽象——只提确实增加后续成本的，不提个人偏好。

## 产出格式
问题清单，每条包含：严重度（阻断/应改/建议）、文件:行、问题是什么、为什么是问题、建议改法。
最后给结论：可合并 / 改后可合并 / 不可合并，并说明还剩哪些未验证项（如未跑的测试）。

## 纪律
- 只报能指出证据的问题；风格偏好标为“建议”且不阻断。
- 不顺手改代码：审查的产出是清单，改不改由实现者（或下一轮）按清单处理，避免审查与实现互相污染。
