# tdd-implement

## 流程
1. **复现/定义**：bug 先写最小复现（失败的测试最好，不能写测试时给可重复的命令序列）；新功能先写验收测试，对着 plan-spec 的验收标准逐条来。
2. **确认红**：运行测试，确认它以预期的方式失败。测试一上来就绿，说明它没测到东西，先修测试。
3. **最小实现**：只写让测试通过所需的代码，不顺手加功能、不顺手大重构。
4. **确认绿 + 全量**：跑新测试，再跑受影响模块的既有测试套件。既有测试变红时，先判断是真回归还是测试依赖旧行为——是后者也要改得有理由并记录。
5. **重构**：绿灯保护下做必要的清理，重构后重跑。

## 纪律
- 不删测试、不放宽断言来让测试通过。测试与实现冲突时，先回到需求判断谁错。
- 每次只推进一个可验证的小步；大改动拆成多次“红→绿”。
- 提交信息/汇报中写清：新增/修改了哪些测试、跑了哪些套件、结果如何。没跑的要明说没跑，不写“应该没问题”。
- 环境跑不了测试时（缺依赖、需外部服务），给出替代验证（静态检查、最小脚本）并明确标注验证强度降级。
