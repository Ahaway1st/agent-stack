# ci-check

## 流程
1. **先定位失败点**：从 CI 日志里找到第一个真实失败（后续失败常是连锁反应），记录失败的 job、步骤和关键错误行，不把整段日志甩给用户。
2. **分类**：代码问题 / 测试问题 / 环境问题（依赖、缓存、超时、限流）/ 偶发（flaky）。分类要有证据，如“本地同命令通过、重跑后通过”才可称偶发。
3. **本地复现**：用与 CI 尽量一致的命令在本地复现。复现不了就说明差异点（版本、环境变量、并行度），不宣称修好。
4. **最小修复**：修根因不修表象。禁止用“重跑直到绿”“放宽超时/断言”“跳过该测试”作为修复手段（除非有证据表明测试本身有缺陷且同步说明）。
5. **确认**：修复后看完整流水线结果，不只看原失败 job——修复可能影响其他 job。

## 汇报格式
失败原因（一句话）→ 证据 → 修复内容 → 复验结果（流水线链接/结论）。偶发失败也要留记录：哪个测试、出现频率、后续观察项。

## 配置变更纪律
改 CI 配置（版本、缓存、并行、超时）时在提交说明里写清为什么；新增密钥引用只写环境变量名，密钥值永不进仓库文件。
