# plan-spec

## 产出格式（一份，可评审）
1. **需求复述**：用自己的话写清要解决什么、给谁、什么不算在内（范围外清单同样重要）。
2. **影响面**：要动的模块/文件、受影响的接口与数据结构、兼容性（旧数据、旧客户端、已有调用方）。
3. **方案**：选定做法 + 一句为什么；备选方案和否决理由各一行，不写长篇论证。
4. **步骤拆解**：有序、可独立验证的小步，每步写明验证方式（哪个测试/命令/人工检查）。
5. **验收标准**：可测量的完成条件列表，与用户需求逐条对应。
6. **风险与回滚**：最可能出错的点、出错的影响、如何退回。

## 纪律
- 规划里出现的每个文件/接口，先用 repo-context 确认存在，不凭记忆写。
- 不确定的地方标“待确认”并列出确认方式；不要用合理猜测填满规格——规格的作用正是暴露未知。
- 规模与任务成比例：三步能说清的不要写三页。规划本身不是交付物，能指导实现和验收即可。
- 用户确认后再进入实现；实现中发现规格错误，先改规格再改代码顺序不可颠倒的部分（接口、数据），其余小偏差在规格中留修订记录。
